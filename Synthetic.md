Making synthetic section IDs negative ensures the lock table can safely store both real sections and synthetic UI-only sections without any collision or ambiguity.
Positive IDs come from the database; negative IDs are generated by deriveSectionKey().

deriveSectionKey(sectionName)

his produces a negative Long such as -48392019.
This synthetic key is used exactly the same way as real DB section IDs (which are positive), but without colliding with them.
So now we have:

caseId = 1234
sectionId = -48392019
userId = “bob”
sessionId = “XYZ”
lockToken = random UUID

Everything after this point is identical to real sections.

2. Acquire Phase (Insert Lock Row)
INSERT INTO case_section_lock (
    case_id,
    section_id,     ← includes negative synthetic key
    section_name,
    user_id,
    auh_id,
    collaboration_session_id,
    browser_tab_id,
    client_type,
    lock_token,
    expires_at,
    last_heartbeat_at
)
The key points:

The negative synthetic section_id gets stored just like a real section_id.
DB doesn’t care whether it’s negative.
Everyone can now “see” that this synthetic section is locked.

The design is intentional:
Positive SECTION_ID → real DB section
Negative SECTION_ID → synthetic section derived from name
This keeps things:

simple
collision-free
future-proof (new sections can appear without schema change)
unified (only one locking table needed)
